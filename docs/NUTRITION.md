# Nutrition

Phases 1–4 provide a food catalog, manual calorie/macronutrient tracker, hybrid food search and persistent conversational meal drafts. A subsequently authorized [NEVO upload/update workflow](NEVO.md) adds English primary names and Dutch aliases from user-supplied CSV files. Open **Nutrition → Diary** (`/nutrition`), **Food products** (`/nutrition/products`) or **Daily goals** (`/nutrition/settings`). The user explicitly approved these phases following the [architecture proposal](NUTRITION_PROPOSAL.md). Calculated recipes and trends remain later phases.

## Using the diary

Choose a calendar date, navigate with previous/next or return to **Today**, which uses the user's saved timezone. The selected date is preserved in the URL and survives reloads. Opening goals from the diary and returning also retains that date. Dates are stored as PostgreSQL `DATE`; changing timezone does not move existing meals between days.

Each day has Breakfast, Lunch, Dinner and Snacks. **Add food** opens conventional product search with the same alias/name ranking as the catalog. Select a food and enter its quantity/unit; the configured default serving is offered first. A missing product can be created inline, then reviewed and saved as a separate consumption entry. Product creation alone does not log a meal. Nutrition previews come from the server, and estimated conversions are labeled.

Each entry captures the product name, full direct nutrition reference, physical/household conversions, source information and per-entry nutrient totals. **Edit** can change quantity, captured unit, meal or date using this stored snapshot exclusively. Product edits, serving removal, archival and even physical source deletion leave historical totals and quantity editing intact. No implicit refresh from current product data is exposed. **Remove** confirms deletion of the selected diary entry.

The daily summary totals the stored calorie/protein/carbohydrate/fat snapshots. Fiber stays explicitly incomplete when any entry lacks it. Display values are formatted to one decimal place; calculations and persistence retain eight fractional digits. Configure your own nullable positive goals in **Daily goals**; nothing is prescribed or filled in automatically. One current set applies to every diary date, with remaining amounts and capped display progress calculated on the server. Effective-dated goals are deferred.

New log requests have a stable request UUID and canonical input hash, unique per owner, to prevent duplicate inserts on concurrent submission or retry. Product versions require reviewing changed source data before a new entry is saved. Entry/goal versions reject stale edits, and all access is scoped to the authenticated owner. Persistent diary, catalog and goals data remain in TanStack Query; form and date interactions are client UI state.

## Using the catalog

Create a product with calories, protein, carbohydrates and fat for an explicit reference quantity: for example 100 g, 100 ml or one named bar. Fiber, brand, description and aliases are optional. Multiple products can have the same name. Search normalizes Unicode, case and whitespace and ranks exact names, exact aliases and then text matches across names, aliases, brands and descriptions.

Add product-specific servings such as one slice = 35 g or one tablespoon = 15 g. Fractional quantities are supported. Choose at most one default serving; mark estimated conversions explicitly. Names/aliases apply only to that product, and serving names are unique within the product.

For serving-based nutrition, name the nutrition serving. Its physical size is optional: a bar can have nutrition without a known weight. Supply the physical size of **one** named nutrition serving to enable weight/volume quantities. Weight and volume require an explicit density in g/ml to cross dimensions. Unknown conversions produce an actionable error; no universal spoon sizes or water-density assumptions are used.

Use **Calculate** for a saved product's quantity preview. The default serving is selected when configured. Calculations run on the server through the same deterministic utility future logging will use; the UI debounces requests and labels estimated conversions. Nutrition values are entered and transported as decimal strings. PostgreSQL stores `NUMERIC(20,8)` and arithmetic uses an isolated Prisma Decimal context with explicit half-up rounding at eight fractional digits. Unknown fiber remains null. Overflow and quantities too small to resolve at storage precision are rejected.

Edit products and servings in one form. A version check prevents stale tabs from overwriting another save. Archiving hides a product from active search; switch to **Archived products** to restore it. There is no normal hard-delete action. Component references restrict serving removal and prevent archiving ingredients of active calculated products.

New products always have manual provenance. Verification is independently editable. Future externally sourced products retain their source identity/version/import timestamp when edited manually; `userModifiedAt` distinguishes those corrections. Dataset imports and AI estimates are not creation options in Phase 1.

## Implementation

- `app/nutrition/products/page.tsx`: explicit Better Auth session check and user-keyed view.
- `app/nutrition/page.tsx`, `app/nutrition/settings/page.tsx`: authenticated diary/goals pages; timezone-derived initial day and validated URL dates.
- `components/Nutrition/`: responsive desktop table/mobile cards, editor, serving controls and saved-product calculator. TanStack Query manages server state; local React state manages form/filter/modal interactions.
- `NutritionDiaryView`, `MealSection`, `LogEntryEditor`, `ProductPicker`, `DailyNutritionSummary` and `NutritionGoalsView` provide the Phase 2 manual diary, inline catalog creation, editable historical entries, summary and goals.
- `lib/nutrition/router.ts`: protected Zod-validated procedures registered as `nutrition` in the root tRPC router. Owner identity always comes from the session; safe errors mask unexpected persistence details.
- `lib/nutrition/products.ts`: owner-scoped services, decimal-string serialization, product-row locks, stable serving IDs, atomic edits, provenance preservation and dependency checks.
- `lib/nutrition/calculations.ts`, `schema.ts`, `normalization.ts`, `search.ts`: deterministic conversion, validation and parameterized ranked text search. No AI/provider access is involved.
- `lib/nutrition/diary.ts`, `goals.ts`, `snapshots.ts`, `diary-schema.ts` and `dates.ts`: owner-scoped diary/goals behavior, versioned snapshot validation/calculation, idempotent creation, exact aggregation and calendar-date semantics.
- `prisma/schema.prisma`: unified `Product`, `ProductServing` and recursive `ProductComponent` relationships. Composite owner/serving foreign keys enforce component integrity. Only direct products are exposed in Phase 1; composition editing and recursive calculation are deferred.

Migration `20261017233210_nutrition_products` is additive and has been applied to the local development database. Other environments require the normal migration workflow and `yarn prisma generate`. In addition to Prisma-generated constraints, its SQL adds positive/nonnegative/finite numeric checks, reference/source consistency checks, direct-cycle prevention and a partial unique index for one default serving. Retain these custom invariants when extending the schema.

The catalog introduces an integer product version alongside the proposal's timestamps to reject lost updates. It otherwise follows the approved Phase 1 design. It adds no dependency, provider abstraction, worker or other-phase tables.

Phase 2 adds `NutritionLogEntry` and `NutritionGoals` through migration `20261017235835_nutrition_diary`, applied locally with the client regenerated. Log-to-product deletion uses `SetNull`, preserving the entry's owner, name and nutrition. The saved serving ID is snapshot metadata with no live foreign key, so serving removal does not block historical edits. JSONB snapshots use schema version `1` and calculation version `direct-v1`; unsupported/malformed snapshots fail safely rather than consulting mutable product data. Recipe support will need an explicit compatible snapshot extension in Phase 5. SQL checks enforce finite/nonnegative nutrients, positive quantities/goals/versions, valid date range and snapshot version; per-owner request uniqueness enforces duplicate prevention.

## Phase 3: related-food search

The catalog offers **Fuzzy search**, which includes related foods using embeddings and remembers its on/off choice in this browser between visits and reloads. Archived products always use conventional search without changing that saved choice. The manual food picker offers **Include related foods**. Conventional search remains the default and works without Ollama. Hybrid search ranks exact normalized names, exact aliases and other literal text matches before semantic-only alternatives, deduplicates by product ID and returns up to 50 candidates. Related foods are suggestions requiring selection; cosine scores are retrieval metadata, not confidence probabilities. Expected provider/configuration failures return conventional matches with a visible fallback notice. Unexpected storage failures remain errors.

`lib/nutrition/product-embedding-*` binds `nutrition.products.semantic` to the dedicated `product_embeddings` table. Versioned text includes normalized food name, brand, description and sorted aliases, excluding nutrition/conversion/provenance numbers. A dedicated `searchUpdatedAt` changes only when that text changes, so nutrient/serving edits keep vectors usable. Owner/archive/freshness filters run before vector ranking. Archiving deletes its vector in the product transaction; physical deletion cascades; restoration queues indexing. Shared collection leases, digest/dimension validation, exact cosine search and atomic replacement are reused. Maintainer authorization is shared with task search; task behavior remains unchanged.

Migration `20261018001956_nutrition_product_search` adds vectors, source timestamps and a coalesced durable owner job, and queues existing active catalogs. Product creation/relevant edits enqueue in their source transaction. The worker captures a revision under a `SKIP LOCKED` claim, renews its lease, synchronizes through the shared engine and acknowledges only that revision/token. Changes during indexing remain pending; crashes recover after five minutes. Failures retain pending work with safe status and exponential retry delays from 15 seconds to one hour. Neither product saves nor HTTP requests launch unawaited inference.

A maintainer chooses an installed embedding model in **Related-food search setup** and confirms a shared rebuild; no model is chosen implicitly. Other users can inspect their own status and queue a retry. Run the worker alongside the long-running Node server:

```sh
yarn nutrition:index --check       # runtime startup only; no data/model requests
yarn nutrition:index               # poll durable jobs until SIGINT/SIGTERM
NODE_ENV=production yarn nutrition:index
# Optional bounded operational run, restricted to one owner:
yarn nutrition:index --once --user <user-id>
```

The worker loads the same Next.js environment files, requires the existing DATABASE_URL/OLLAMA_BASE_URL, and uses `tsx` as its sole new runtime dependency. Configure restart-on-failure in the deployment's process supervisor; this repository has no deployment supervisor to modify. It drains active work before stopping. Without a running worker, queued changes persist and conventional search remains available. Full product rebuilds retain the shared in-memory staging design, originally bounded to 1,000 active documents and 2,000,000 vector values per operation. The authorized NEVO workflow extends these bounds to 10,000 documents and 12,000,000 vector values to fit the supplied dataset. Larger catalogs/models need a separately scoped staging design. These optional collection bounds do not change task indexing.

## Phase 4: saved conversational meal drafts

On the diary, choose **Describe a meal**, explicitly select an installed chat model, and describe foods/amounts. The first request creates a saved draft; subsequent messages correct that same draft. Closing the dialog keeps it in **Resume a saved meal draft**. The `draft` URL parameter restores an authorized draft after reload. Model selection is fixed for that draft, independently of embedding models. No food reaches the diary until **Confirm and log meal**.

Review the selected foods, quantities, units, meal and date. A unique exact name or alias may select a product automatically; multiple exact matches and partial/semantic alternatives require selection. Missing amounts remain blank. Household names, aliases and common plurals resolve only through that product's configured servings; unknown conversions remain unresolved. Candidate buttons and **Edit draft food** allow explicit choice, unit/quantity edits and inline manual product creation. Foods can be added/removed manually. Save date/meal changes explicitly. Nutrition is computed by the same deterministic snapshot utilities as ordinary logging; previews label estimated conversions and total only resolved foods.

When there is no exact name or alias, draft suggestions prioritize embedding-based related foods over partial text matches. The search merges and deduplicates both result pools before limiting to five suggestions, so alphabetically early products containing “rice” cannot crowd out the related-food results. Catalog and manual picker ranking stays text-first. A unique exact match still resolves without embedding inference; unavailable related-food search falls back to text matches with a notice beside the unresolved draft food. Each embedding search has a 12-second timeout within the draft's overall deadline. No additional food-search model or autonomous agent is used.

The model emits validated `addItem`, `removeItem`, `setQuantity`, `changeProduct`, `changeMealCategory` and `changeDate` operations, never database writes or nutrient values. Stable application-generated item IDs survive corrections. Invalid IDs, malformed output or invalid operation batches preserve the existing draft. Application services apply the complete batch after model/matching work, with a revision/token check. Date interpretation receives the saved timezone, authoritative today/yesterday, selected draft date, recent messages and current item IDs. Ambiguous dates/questions remain visible for explicit acknowledgement; unresolved foods/quantities always block confirmation.

`NutritionMealDraft` owns a bounded JSONB array of stable items, captured product definitions/versions, candidate summaries, user-review questions, date/category, status and generation lease. `NutritionDraftTurn` saves each user message before generation, then its reply or safe failure state. Items are a validated document rather than separate mutable rows: the whole draft is the revision/transaction boundary, capped at 40 foods. There are at most 20 open drafts per owner and 40 messages per draft. This keeps the initial implementation small while preserving stable identities and authoritative server state. TanStack Query owns drafts/history; only unsaved fields and dialog state are local React state.

A three-minute lease protects one interpretation per draft. The shared structured helper limits inference to 120 seconds; matching and publication share a 150-second deadline. Product semantic queries have a 12-second signal, forwarded through shared resolution/inference. Ordinary task-search defaults stay unchanged. Reads recover expired generations as failed messages. Manual edits supersede in-flight replies, and late responses cannot overwrite them. Stored message IDs make retries/replays idempotent; retries of older failed messages after a newer completed correction are rejected. UI retries retain request IDs after a lost response, and old asynchronous replies cannot clear a newly opened form.

Confirmation locks the owner draft and source products in a stable order, checks the draft/product revisions, validates every quantity/conversion and uses the shared transactional diary insertion service. It writes all snapshots/entries and marks the draft confirmed atomically. Concurrent/repeated confirmation returns the saved entry IDs without inserting again, even if entries are later removed. Source edits, archival or deletion refresh/clear affected draft references without inserting logs, return a visible review notice and require another confirmation. Saved diary history remains independent of these changes. **Discard draft** confirms closure without logging and retains its conversation/status.

The new shared server-only `generateStructured` helper in `lib/ai/structured.ts` uses the installed AI SDK's `generateText` / `Output.object`, caller-supplied Zod schema and explicit shared model resolution. It bounds context at 64,000 characters, output at 4,096 tokens, inference at 120 seconds and retries at zero; cancellation is forwarded. Ollama thinking is disabled for these structured calls to reserve output for the validated document. Domain prompts/operations/matching stay under `lib/nutrition/`; the helper does not depend on Nutrition or AI Dev.

Migration `20261018015500_nutrition_meal_drafts` is applied locally and Prisma Client regenerated. SQL checks constrain draft status/lease/date/document bounds, provider/model identity and message lengths. All draft procedures authenticate and enforce owner scope; manual catalog/diary/goals paths remain independent of model availability.

### Phase 4 validation and limits

Live structured-output validation used only synthetic fixtures on the configured LAN Ollama endpoint. `qwen3:8b` successfully interpreted two foods, applied a stable-ID quantity correction, retained the other food and moved the meal to authoritative yesterday. Thirty PostgreSQL/model checks passed, covering saved conversation, ambiguity, unknown food, owner denial, source-version refresh, forced transactional rollback, concurrent/repeated confirmation, immutable historical values, superseded replies, expired leases and discard. Initial `llama3.1:8b` responses were schema-valid but omitted a category or food; operation-first schema ordering, explicit multi-food examples and non-thinking generation improved the tested `qwen3:8b` flow. These are retrieval/interpretation fixtures, not a guarantee of model accuracy. Review remains mandatory, and no model is silently selected or switched.

Browser verification covered explicit model selection, a two-slice breakfast draft, a conversational correction to three slices plus banana, reload restoration, manual 3.5-slice editing and exact confirmed totals (413.05 kcal). A changed-source preview required a second confirmation and preserved the earlier 306.25-kcal bread entry. An unavailable-model message stayed saved and its draft could be discarded. Desktop and 390px mobile review layouts fit without horizontal overflow; Next.js runtime diagnostics were clean. All synthetic users/products/logs/drafts/turns and their queued work were removed, and the isolated browser was signed out/closed.

Recipes/composite calculations, analytics, recent/frequent foods and copying meals remain deferred. There is no lookup of a user's "usual" meal or yesterday's recipe: the draft asks for clarification rather than inventing those references. Generation leases recover crashes; they do not guarantee preserving an in-flight model's unsaved partial response. Indexing requires explicit maintainer setup and the documented worker process; no deployment supervisor or provider/model default was added.

## NEVO dataset management

Use **Food products → Upload NEVO dataset** to preview and apply the original CSV. New versions match by NEVO code, use English names with full Dutch aliases, preserve manual edits by default and leave historical diary entries unchanged. Original source rows are kept separately from editable products, and NEVO calculations include source/version attribution. See [NEVO upload and updates](NEVO.md) for mapping, update policy, limits and validation.
